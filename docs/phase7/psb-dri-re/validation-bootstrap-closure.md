# Remaining interface and bootstrap contracts for the bounded path

This continues the [bounded scene trace](bounded-path-closure.md). It compares retained `psb_dri.so` (SHA-256 `74ca42991906741ee91be1bc088ae0b142fa71b6a85658c5dad0851ce50dd0d8`) and `Xpsb.so` (SHA-256 `da531587b1ec59fe433fa20ddd2e691b2f8b7fb35bb82525d4db99259c5e571f`) with the separately recovered public `psb-kernel-source-4.41.1` (`psb_drm.h` SHA-256 `b4aeb1f85c5609c5811447f2c1ea691a4dbaedb439955df507b51b8302769494`), DDX 0.32.0 and libdrm-poulsbo 2.3.0 source. Binary observations are CONFIRMED within each ELF; source-defined behavior is CONFIRMED for its own release; cross-component compatibility remains INFERRED until an exact built stack is identified.

## BO validation, relocation and fence

`psb_dri.so:0x00037b51` builds chained validation records before `drmCommandWrite(fd, 0, ..., 0x90)`. Each record is zeroed as `0x22` 32-bit words (`0x88` bytes), then receives the next pointer, BO handle, flags/mask/hint and related request fields drawn from a retained BO list. On success the routine reads handled/return and reply fields back, then resets its submit buffers; it retries the direct command on `-11` (`-EAGAIN`). The candidate `libdrm-2.3.0/shared-core/drm.h:764–859` defines a `drm_bo_op_arg` of the same 136-byte i386 layout: eight-byte `next`, a request/reply union, then `handled` and padding. The candidate kernel `psb_sgx.c:410–500` requires `drm_bo_validate`, walks `next`, validates each handle with request flags/mask/hint, and checks a presumed offset. **CONFIRMED:** binary record width and call behavior; source structure and consumer behavior. **INFERRED:** that the named structure is the exact linked ABI (P7F-006).

The binary relocation helper `0x00037854` advances its cursor `0x28` bytes and writes an offset operation, destination word index, source BO-list index, mask, combined shifts, pre-add, background and destination BO-list index (the first eight candidate fields). It can place `0x67676767` in the destination before validation when an offset is not yet known. The candidate `psb_drm.h:143–154` defines ten 32-bit words; its final `arg0` and `arg1` are not written by this helper on the inspected path. The candidate kernel `psb_sgx.c:631–782` validates BO-list indices and pre-add, chooses a relocation operation, computes a BO/GPU offset or USE base, shifts/masks it and writes the destination. It may skip relocation when a presumed offset is still correct (`psb_sgx.c:384–406,818–899`). Thus selected offset-relocation arithmetic is **reconstructable as a candidate ABI**, while exact address values and other operation variants remain UNKNOWN without a matched build and target address-space contract.

The `0x90`-byte command at `0x00037b51` is narrower than a generic unknown ioctl. For selector `0` the binary sets engine word `+0x5c` to `3`, TA flags `+0x20` to `3`, TA size `+0x2c` from output bytes/4, validation pointer `+0x00`, scene pointer `+0x10`, fence pointer `+0x18`, relocation handle/offset/count `+0x48/+0x4c/+0x50`, and fence flags `+0x58` from its caller. The candidate header names engine `3` `PSB_ENGINE_TA` (`psb_drm.h:161–165,221–263`). The candidate kernel uses `buffer_list`, applies relocations, obtains TA and command BOs, copies/allocates a scene pool, and queues a TA task (`psb_sgx.c:1237–1435`; `psb_schedule.c:1230–1294`). These are source-family interface correlations, not proof that the retained binary succeeded against that exact module or the modern gma500 driver.

For a hypothetical clean-room call, the following **required values remain unestablished**: every BO's placement/flag/mask/hint and presumed-offset state at creation; the exact validation-list order and count for the selected scene; valid GPU addresses/use-base assignment; the scene pool's handle and width/height contract under the exact paired build; complete feedback/oom and fence choices; and accepted error/retry transitions. The source gives algorithms for parts of validation, but the binary-to-exact-build pairing and upstream resource-producing state are missing. This is more precise than saying that the entire ioctl format is unknown.

The binary's successful submit path can create a `SuperFence` unless its flag suppresses a user fence. The candidate kernel's `psb_fence_or_sync` creates a fence or idles the engine on failure (`psb_sgx.c:1014–1088`), and `psb_cmdbuf_ta` queues TA/raster actions then reports fence progress (`psb_schedule.c:1230–1294`). It returns BO-validation replies except on `-EAGAIN` (`psb_sgx.c:1091–1130`). This establishes historical **source** behavior, but the exact required wait point for one GL draw, retained binary fence lifetime across swap/finish, and safe recovery from a failed actual GPU operation remain UNKNOWN. No historical retry is a safety guarantee for this machine.

## GL entry versus a proposed frontend

The retained ELF installs its private 0x68-byte render table at context-derived `+0x728`; `0x0002d124` chooses that or a second table at `+0x724` using context flags `+0x720`, `+0x76c`, `+0x778`, and `+0x77c`, then calls `clip_set_render` (`0x000dd16d`). The latter stores the table at clip `+0xf8`; the clipping pipeline propagates it to pipe `+0x103c`, and a `+0x1c` dispatch can reach indexed draw `0x00026896` for the selected mode-3 table ([draw trace](draw-to-submit.md), P7E-007). `0x00027fa0` then calls `0x00029251` to process dirty bits and reaches the selected scene-state case above.

The binary supplies a possible indirect state-atom dispatch edge for `0x0002d124`: relocation at ELF VA `0x002b3374` places that function in the callback field of a 16-byte atom at `0x002b3368`, whose first-word mask is zero and second-word mask is `0x74`. Relocation at `0x002bb208` places the atom in a static pointer array. `0x0004f3ef` walks the context's atom pointer list at `+0x698` (count `+0x69c`), tests two dirty words at `+0x690/+0x694` against atom masks at `+4/+8`, calls the callback at `+0xc`, then clears both dirty words. `0x00048592` initializes both dirty words to all ones, and `0x00052fcc` can OR bit `8` into the second. `0x0002b3d4`, called by context setup `0x000371f0`, allocates `0x44` bytes, copies the 17-pointer static array beginning at `0x002bb200` into context `+0x698`, and sets count `+0x69c` to `0x11`. This closes array installation and makes the atom containing `0x0002d124` reachable through `0x0004f3ef` when its mask intersects the dirty state. The bytes, relocations, installation and conditional dispatch are **CONFIRMED** within the retained ELF (P7F-010/P7F-011). The exact Mesa GL entry, conditions that set this mask for one selected draw, and primitive/vertex-array validation remain **UNKNOWN**.

A future modern frontend need not reproduce the historical GL dispatch implementation verbatim. It would need an independently specified lower interface that supplies the selected primitive, validated vertex/index resources and complete state inputs. Such an interface is a **proposed architecture**, not recovered behavior. It does not eliminate the missing program/TA bytes or kernel ABI/bootstrap requirements.

## Bootstrap dependencies and ordering

The public DDX source opens/uses DRM and calls `psbDRIScreenInit` early in `src/psb_driver.c:1366–1397`; `psbDRIFinishScreenInit` precedes the conditional `XpsbInit` call at `:1547–1564`. Its `src/psb_dri.c:577–582` exposes a DRI client driver name only when acceleration and `xpsb` are enabled. This is **CONFIRMED DDX-source order**, not an assertion that the exact retained binary always ran or that `XpsbInit` completion is an SGX hardware requirement.

Inside retained `Xpsb.so:0x2690`, the historical path checks DRM major `4` and BO major `1`, allocates private state and an XHW BO, creates BO pools, uploads the 440-byte static source to a BO, initializes dynamic shader/geometry/render-register BOs through `Xpsb3DContextInit` (`0x51c0`), derives `regMap+0x40000`, calls `Xpsb_set_vopt` and `Xpsb_sgx_initialize` (`0x3820`), allocates a further large BO, sends direct XHW init request `1` with `0x14` bytes, maps another BO and starts the XHW thread. This is **CONFIRMED conditional binary order** (P7F-007). `0x3820` contains historical SGX MMIO **writes**; it is not authorization or a safely reproducible reset/clock sequence. The 440-byte source is not identified as firmware, and the recovered `psb-firmware` 0.30-4 package's MSVDX-only result stands.

## Exact version pairing remains open

Both retained ELFs and the public 4.41.1 kernel source contain `5.0.1.0046`; direct request indices `0–3`, `0x90` command size, `0x14` XHW/scene sizes, and the `0x88` validation-node size now reinforce a **strong release-family** correlation. The DDX source supplies a structurally matching 32-byte `PsbDRIRec` but asks the loader for `XpsbTakedown` while the ELF exports `XpsbTakeDown`. The candidate libdrm-poulsbo 2.3.0 source packages an older PSB header label and does not authenticate the linked library. The DDX spec requires package families but pins no exact builds; the retained xpsb spec is 0.18-4.1 while a contemporary index lists 0.18-5. The [XHW ioctl direction difference](../xpsb-re/version-pairing.md) remains a source-level difference, but the candidate DRM core dispatches this request by number and copies its input according to the caller's direction; it is no longer an unresolved candidate-source dispatch blocker. **Exact five-way pairing is UNKNOWN** (P7F-008); no source/metadata item inspected here provides a build manifest or matching built DDX/libdrm/kernel hashes.
