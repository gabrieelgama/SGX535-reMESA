# Minimal PDS read-set hypotheses from retained CPU generators

This is a static CPU-side constraint result, not a Series5 PDS decoder. The [semantic corpus](pds-semantic-corpus.csv) reclassifies the existing 42 rows by emitter, data-prefix writes and code context; the [differential matrix](pds-differential-matrix.csv) and [bit influence table](pds-bit-influence.csv) are generated by [the authorial script](../../../tools/psb-dri-re/pds_semantic_constraints.py). `UNKNOWN` in those files means no GPU field or read behavior was established. The script does not execute an historical ELF.

## A fitting, falsifiable word model

For the three retained low-`0x45` words, the following *arithmetic decomposition* fits the CPU stores:

```text
word = 0x07000345 | (A << 18) | (B << 13) | (C << 16)

word         A  B  C  corresponding initialized CPU data
07000345     0  0  0  primary: +00/+04 and +20
07042345     1  1  0  secondary: +08/+0c and +28
070b0345     2  0  3  mixed event: +10/+14 and +20
```

The mixed event CPU stores are visible in DRI `0x392ab`: relocation at `+0x10`, zero at `+0x14`, and `8` at `+0x20`; its final `0x070b0345` is at `+0x8c`. The earlier simple two-index construction failed to explain this word. The refined decomposition explains the *bits*: its `0x00080000` difference from `A=0` tracks the candidate DS0 pair, and `0x00030000` is residual `C=3`. It does not establish that `A` or `B` is a hardware source field, that `C` is a destination/mode field, or that the instruction reads exactly three dwords. All three words are literals; no caller varies `A`, `B`, or `C` in a common `0x45` constructor.

There is a weaker cross-class check: vertex `0x2f030343` → `0x2f070343` adds bit 18 when an optional `+08/+0c` DS0 pair is initialized. Xpsb's event word `0x07070365` has bits 16–18 set and follows a relocation/zero pair at `+08/+0c` in emitter `0x7eb0`. These correlations strengthen the pair-index interpretation, but neither is an untouched `0x45` instruction generated from a controlled varying input. DRI and Xpsb may also share source lineage.

M1 and M2 differ in the **read-count/completeness interpretation of fixed bits** of `0x07000345` (or a fixed implicit source), not in a bit that any retained CPU constructor varies. The observed `0x00042000` pair delta constrains bits 13 and 18, while the mixed-event word leaves bits 16–17 (`0x00030000`) without an isolated semantic producer. All 42 corpus rows are CPU *emissions*, so none observes the GPU reading or ignoring a data slot. This makes M1 and M2 observationally indistinguishable by the retained CPU-side generator evidence, even after the arithmetic counterexample is fitted. The exact `0x45` source count and the `0xaf` read behavior are the first unresolved semantic dependencies; all nine producer-unwritten selected dwords remain possible reads.

## Terminal-word constraints

A targeted immediate-store survey of the retained `.text` found 11 DRI `0xaf000000` stores (ELF VAs `0x263e4`, `0x28fdb`, `0x29d26`, `0x39693`, `0x39723`, `0x39bd9`, `0x39e21`, `0x3a7ec`, `0x3fafa`, `0x406f3`, `0x4286a`) and four Xpsb stores (`0x8203`, `0x8890`, `0x8a47`, `0x8b48`). In the decompiled builders checked, the word is CPU-final for each PDS-shaped subprogram. DRI `0x3faa3` requests only four bytes for this word with allocation data-dword count zero, commits exactly one dword, then clears the returned descriptor's `+0x0c/+0x10/+0x14` fields. The DRI mixed event builder `0x392ab` stores it at both `+0x50` and `+0x90` in one larger BO, so it is not necessarily terminal for an entire BO. This is strong **CPU program-grammar** evidence for a terminator without local constant data in the standalone case, not proof of zero architectural source reads or of its reads in the selected primary program. The immediate survey did not identify analogous `0xad`/`0xae` immediate stores; that limited negative result is not a full word-class census.

## Why deterministic fill is not yet a substitute

The selected 12-dword data prefix includes nine slots with no selected producer write. Writing zeros to them in a clean-room program would fit within the committed data prefix, but neither the retained CPU behavior nor an independently established PDS contract proves that every such slot is padding. A fresh or cleared BO merely chooses zero as an input; it does not prove that hidden reads of zero preserve the intended USE task or other state. Thus deterministic filling does not close the read-set dependency under the project's implementation-grade proof standard.

The smallest distinguishing evidence is a valid SGX535-applicable rule fixing the `0x45` instruction's complete source count and selectors, plus the `0xaf` class's data-store/implicit reads, or an independent target-equivalent read trace under an authorized gate. The unavailable PDF is not a prerequisite for continued static work, and no restricted PSP2 definition is used here. FG-02 remains OPEN. Gate B remains BLOCKED; hardware functionality remains UNVERIFIED.
