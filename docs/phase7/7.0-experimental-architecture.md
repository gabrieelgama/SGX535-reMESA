# 7.0 — Experimental architecture and safety requirements

The purpose is to determine whether an SGX observation can be designed under the current gate. Mechanism and safety are separate: historical code shows how a read was issued; it does not prove that the same transaction is harmless in the proposed state.

| mechanism | Phase 7 decision | reason |
|---|---|---|
| userspace BAR access | prohibited | no owner/lifetime/PM protocol |
| `/dev/mem` | prohibited | bypasses existing ownership |
| `resourceN` mmap | prohibited | resource visibility is not an SGX access contract |
| separate module/PCI owner | prohibited | no justified independent owner or exclusion protocol |
| fixed-purpose gma500 instrumentation | preferred research direction; BLOCKED | uses existing ownership but lacks read, power, failure and locking proof |
| existing passive kernel interfaces | GO within Gate A's scope | exported inventory can support provenance; cannot identify internal SGX state |

The next documentary review would need the following before selecting a mechanism:

- **Preconditions:** verified target identity and installed kernel; exact candidate identity/width; revision and errata coverage; documented power/clock/reset and pre-initialization requirements; live owner mapping; exclusion against PM, IRQ, 2D/KMS activity and removal.
- **Abort conditions:** missing or contradictory precondition evidence; unexpected kernel/module identity; unverified power state; any need to wake, reset, probe adjacent offsets or add fallback reads. Abort before MMIO. A stalled CPU read cannot be assumed abortable after issue.
- **Failure model:** CPU completion, exception, timeout/stall and platform side effects must be bounded by applicable evidence. None is established for an unavailable Poulsbo SGX block.
- **Recovery requirements:** prove that the selected recovery applies to the exact failure mode and remains available if a CPU/interconnect stalls.
- **Logging:** record source/build/config hashes, BDF and revision namespaces, context and synchronization evidence, precondition evidence, exact approved operation, pre/post logs and disposition. Never log a guessed returned value.
- **Reproducibility:** repeated observations under documented equivalent conditions, retaining failures as well as successes. A single plausible result is OBSERVED at most and cannot establish a side-effect-free architectural rule.

These are acceptance requirements, not a TV1 recipe or executable interface. The [ownership analysis](7.0-ownership-locking.md) and [failure review](7.0-failure-recovery.md) leave essential preconditions unmet.
