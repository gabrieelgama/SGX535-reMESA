# 7.0 — Failure and recovery boundary

No inspected source defines the CPU-visible outcome of either identification read when Poulsbo SGX is unpowered, gated, reset, partly initialized, suspended or transitioning. Completion, stale/all-zero/all-one data, abort, exception, timeout, CPU stall and platform hang remain UNKNOWN. This is the bounded result of the prior source search and present source recheck, not a claim that all outcomes occur.

P7-006 shows that the 5.10.240 header still contains a disabled `TRAP_SGX_PM_FAULT` branch ([psb_drv.h](../phase4-2-data/antix-source/drivers/gpu/drm/gma500/psb_drv.h):893–907). It tests a port-read result, emits a warning and then reaches `ioread32`. It cannot supply a fail-closed check or a timeout for that read. Enabling it would introduce another hardware access and is not proposed.

P7-005 shows `psb_spank()` asserting and releasing SGX reset fields in the 2D implementation. This proves historical software writes, not recovery from a stuck CPU MMIO transaction. The historical PSB watchdog similarly addresses its own task/lockup flow (P3-044), not the missing failure boundary.

The existing [recovery plan](../recovery-plan.md), SysRq documentation (P4-017) and pstore/ramoops documentation (P4-018) describe diagnostic facilities. Their availability on this Dell and ability to recover the possible read failure are not established. Reboot or power cycling must not be advertised as a proven remedy.

No timeout wrapper, IRQ mask, module reload, reset or retry is accepted as a substitute. Recovery and CPU completion remain independently blocking.
