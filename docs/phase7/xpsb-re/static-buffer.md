# The 440-byte Xpsb static buffer

This is a static trace of the retained [Xpsb.so](binary-inventory.md), SHA-256 `da531587b1ec59fe433fa20ddd2e691b2f8b7fb35bb82525d4db99259c5e571f`. Addresses are ELF virtual addresses; Ghidra's disposable image base adds `0x10000`. The bytes remain in the retained binary and are not reproduced here.

**CONFIRMED source:** the exact range is `.rodata` ELF VA/file offset `0xd0e0..0xd297` (440 bytes, SHA-256 `8b5e46addd6e1d5c98eb16787cb23c74196c56d8aa5bd729b26f56a6026f7fbe`). The section is non-writable in the ELF. A [read-only Ghidra XREF sweep](../../../tools/xpsb-re/TraceStaticBuffer.java) over all 440 addresses found three direct references, all to `0xd0e0`: `0x267e` in `XpsbShaderCode` and `0x2b7d`/`0x2b93` in `XpsbInit`. No ELF relocation targets the range. This describes static references, not all possible runtime address arithmetic.

**CONFIRMED upload/lifetime:** `XpsbInit` (`0x2690`) calls `XpsbGenBuffers` (`0xae70`) with the label `USSE static buffer`, count one and a `0x10` fifth argument; `XpsbGenBuffers` allocates a 0x28-byte wrapper kept at private offset `0x7c`. `XpsbBOData` (`0xbaa0`) allocates backing storage when needed, maps it, copies all `0x1b8` bytes from `0xd0e0`, and unmaps. Failure paths in `XpsbInit` unreference the wrapper. `XpsbTakeDown` (`0x2f10`) unreferences it on normal teardown. These are paths in historical software; no BO operation was executed in this investigation (P7D-001/P7D-002).

The range is structured, but its hardware interpretation is not established. The first `0x110` bytes include repeated 16-byte records with two nonzero 32-bit words followed by zero and `0xf8000140`; the remaining `0xa8` bytes contain different word patterns. This is **CONFIRMED byte structure**, not an instruction decode. Exact-word searches of the retained TI sources and SGX535 register/feature snapshots did not identify a sourced instruction interpretation; those headers are not ISA manuals. The complete 440 bytes are uploaded; no static parser identified a firmware header or a microkernel entry point.

There is one **CONFIRMED CPU-side consumer of the original `.rodata`**. `XpsbShaderCode` (`0x2670`) returns `0xd0e0 + byte_offset`. `XpsbCompositeShader` (`0xa660`, call at `0xa76a`) reads a 14-entry offset table at `0xd740` containing `0x30, 0x40, …, 0x100`. Its parallel 14-entry table at `0xd700` is all zero in this ELF. For an index within those 14 entries, the zero branch reads two words from the selected source offset and copies them after two dynamically selected words into a 16-byte output record. The output pointer advances by 16 bytes. This places selected source words in the X-server composite shader-construction path (P7D-003). The exact meaning of the four-word record and whether the eventual GPU executes it are **UNKNOWN**.

The internal X-server composite chain is now bounded more tightly: `psb3DPrepareComposite` (`0x5ee0`) maps a different BO at private `+0x1d0`, calls `XpsbCompositeShader` with that BO's mapped output pointer, then passes its output descriptor to `Xpsb_emit_pixel_shader` (`0x82c0`). That function invokes `Xpsb_emit_use_relocation` (`0x8d90`), which creates register/offset relocations through named helpers. `psb3DCompositeFinish` (`0x5c40`) later unmaps the BO and calls `XpsbFlush3D` (`0x9f70`), which submits direct command index 0/`0x90` bytes. The public DDX source calls the exported prepare and finish functions at `src/psb_composite.c:200,297`; exact DDX binary pairing is still UNKNOWN. **CONFIRMED:** these internal ELF call/data edges exist. **INFERRED:** a compatible historical Xorg composite operation can carry selected source words into the index-0 submission path. This is the X-server composite path, **not** the DRI GL draw path and not proof of GPU execution (P7D-009).

A decompiler scan of 246 non-external functions found direct accesses to the private `+0x7c` wrapper in `XpsbInit` and `XpsbTakeDown`, but did not establish a later direct CPU consumer of **the uploaded BO**. That negative static result does not rule out indirect access, stored device addresses, or a GPU-side consumer. The observed composite path reads the original `.rodata`, not the uploaded BO. The purpose of the `0x110..0x1b7` tail and the BO's eventual device address or relocation remain **UNKNOWN**. Therefore the blob is not classified as firmware, a microkernel, or proven executable code.

The source-copy path is separate from the [DRI client's generated USC/USSE and PDS paths](../psb-dri-re/sgx-specific-findings.md). An identical program format or shared device address has not been established.
