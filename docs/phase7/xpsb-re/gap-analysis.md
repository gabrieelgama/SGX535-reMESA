The public DDX source, retained `Xpsb.so` and `psb_dri.so`, candidate `libdrm-poulsbo` 2.3.0 source and newly found 4.41.1 PSB kernel source describe much of the **historical software interface**. The graph is not an authenticated matched installation: both ELFs and that kernel source embed `5.0.1.0046`, and direct ioctl argument sizes agree, but the older retained kernel snapshot labels `5.0.0.0045`, the candidate libdrm source RPM includes `2.2.0.32L.0027` PSB headers, and the 0.32.0 DDX source has an `XpsbTakedown` loader-string spelling mismatch. The matching built DDX, libdrm and kernel binaries remain UNKNOWN ([pairing details](version-pairing.md)).

**Later P7E finding:** [the private draw/frame-tracker map](../psb-dri-re/draw-to-submit.md) resolves the indirect mode-3-exit → scene-finalization → index-0-submit edge. The table and earlier checkpoint text below retain their original evidence scope; the full GL frontend and program/packet contract remain open. The strict [readiness decision](../psb-dri-re/clean-room-readiness.md) is Result B.

The extracted `xpsb-glx` package contains `Xpsb.so`, `psb_dri.so`, `psb_drv_video.so` and libtool files; it does **not** contain an independently identified SGX firmware or microkernel file. The [440-byte `.rodata` trace](static-buffer.md) establishes the BO upload and a separate CPU-side composite-template use, but no consumer of the uploaded BO or instruction format. Neither use proves a firmware/microkernel role or Dell applicability. `psb_drv_video.so` remains unanalyzed and may matter to video; its SGX 3D relevance is UNKNOWN. The public `psb-firmware` 0.30-4 package supplies only the MSVDX/video `msvdx_fw.bin` named by the candidate kernel's MSVDX path; it is not an identified SGX payload ([dependency inventory](bootstrap-dependencies.md)).

The strongest remaining static targets are: (1) authenticate a matched 0.18-era Xorg DDX, `libdrm.so.2` and PSB kernel binary/source version; (2) recover exact XHW shared-buffer layout and all request/reply fields; (3) finish BO validation, relocation and fence layouts against the matched kernel; (4) trace the DRI scene-finalization trigger; (5) identify the uploaded static BO's actual consumer; and (6) inspect any other independently identified SGX bootstrap inputs. These are tracked in [the updated unknowns](unknowns.md).

A clean-room **interface specification for the reconstructed subset** can now be drafted: the DRI record, selected XHW request flow, candidate BO/fence ioctls, and bounded command/scene paths. There is **not** enough evidence to specify a minimal interoperable 3D implementation end to end. Exact paired ABI details, complete graphics command formats, SGX program semantics, initialization dependencies, physical revision applicability, power/clock/reset requirements and safe failure/recovery behavior remain open. Hardware validation would eventually be required to establish that an independently written implementation works on the Dell, but static archaeology and authorized primary documentation should close the software-contract gaps first. The existing controlled-read safety gate is still BLOCKED.
