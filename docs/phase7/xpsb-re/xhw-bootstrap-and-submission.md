# X-server SGX bootstrap, XHW and submission

The retained `Xpsb.so` is more than an Xv/composite facade. Its `XpsbInit` (`0x2690`) calls `drmGetVersion` and `drmBOVersion`, accepts major versions 4 and 1 respectively, allocates a 0x140c-byte private object, creates/maps an XHW communication BO, creates several BO pools, allocates dynamic shader/geometry and render-register buffers, and starts a kernel-request thread after the XHW-init command succeeds (P7C-009). These are **CONFIRMED static binary paths**, not proof that they ran successfully with any particular stack.

The DDX source passes `regMap` and a DRM fd to `XpsbInit` ([boundary](dri-boundary.md)). In the retained binary, `XpsbInit` derives `regMap + 0x40000`; `Xpsb_sgx_initialize` (`0x3820`) writes several offsets through that pointer, and `Xpsb_set_vopt` (`0x4af0`) reads relative `0x14` as an input to revision-dependent options. The DDX source calls the offset `PSB_THALIA_OFFSET` (`src/psb_driver.h:1163–1178`). This establishes the historical X-server module's **direct SGX MMIO behavior** (P7C-010). It does not establish safe semantics, the Dell's physical core revision, clocks, power, reset preconditions, or permission to repeat those accesses. Gate B and the empty read whitelist are unchanged.

At `0x2690`, a 0x1b8-byte `.rodata` region at ELF VA/file offset `0xd0e0` is passed to `XpsbBOData` (`0xbaa0`) for a BO labeled “USSE static buffer.” `XpsbBOData` maps the BO and copies the supplied bytes into it. The region's SHA-256 is `8b5e46addd6e1d5c98eb16787cb23c74196c56d8aa5bd729b26f56a6026f7fbe` (P7C-011). This is a confirmed static-data-to-BO copy path. It is **INFERRED** that the bytes represent a GPU program; their instruction format, target revision, actual execution and relationship to a microkernel are UNKNOWN. The blob is not copied into documentation or implementation.

The direct XHW calls observed in the binary are tabulated in [ioctl-map.csv](ioctl-map.csv). `XpsbInit` uses index 1 and 20 bytes, then the `XpsbThread` entry at `0x30f0` waits with `drmCommandNone(fd, 2)`. The thread dispatches operations 0–11 from its mapped communication BO to render/TA kick, scene allocation or binding, TA memory handling, reset-like initialization, lockup checks and termination routines. The archived PSB kernel source names indices 1 and 2 `XHW_INIT` and `XHW`, maps the supplied communications BO, queues requests, and copies replies (`PSB_psb_xhw_c.txt:416–470,516–580`). This is an **INFERRED cross-artifact match** supported by index, size and shared-BO pattern (P7C-012); exact paired kernel revision remains UNKNOWN.

`XpsbFlush3D` (`0x9f70`, call site `0xa325`) validates its BO list, constructs a 0x90-byte argument, sends direct index 0 through `drmCommandWrite`, handles retry/error and fence paths. `XpsbFlush3DVideoBlit` (`0x9a10`) calls an anonymous function at `0x9620`, which also submits at `0x981b`; this path's full higher-level caller chain remains UNKNOWN. The archived PSB kernel source calls index 0 `CMDBUF`; its handler validates chained `drm_bo_op_arg`s, applies `drm_psb_reloc` entries (40 bytes each), selects engine-specific handlers, allocates/looks up scenes, and returns fence feedback (`PSB_psb_drm_h.txt:143–165,221–263,338–345`; `PSB_psb_sgx_c.txt:410–450,818–899,1237–1430`). This gives a bounded static X-server-to-kernel command path, not a working submission protocol (P7C-013). The separately recovered [DRI client path](../psb-dri-re/command-submission.md) also reaches index 0; no direct call from one ELF into the other's submit wrapper has been established.

```text
Xorg DDX source 0.32.0 ──(regMap, drmFD)──> Xpsb.so 0.18 binary
       │                                      ├─ XHW shared BO + index 1 init
       │                                      ├─ index 2 request thread ↔ historical PSB XHW handler
       │                                      └─ BO/reloc/fence + index 0 CMDBUF ↔ PSB submit handler
       └─ PsbDRIRec via DRIInfoRec ──> psb_dri.so DRI callbacks
                                              └─ BO/reloc/fence + index 0 CMDBUF ↔ PSB submit handler
```

Solid arrows denote a binary observation or source-defined interface **within its own artifact**. Cross-artifact arrows are version-correlated **INFERRED** links until matched build manifests or binaries prove exact compatibility. The already recovered `GL/driver state → PDS/USC/USSE → scene/TA → command submission` chain remains documented in [P7B](../psb-dri-re/final-report.md); this new XHW branch does not prove the full GL draw-to-submit edge.
