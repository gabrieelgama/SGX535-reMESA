# External bootstrap and payload inventory

The public RPM Fusion Xorg DDX source spec requires `kmod-psb`, `psb-firmware`, `xpsb-glx` and `libdrm-poulsbo` (`xorg-x11-drv-psb.spec:46–50`). This confirms packaging dependencies, not which component initializes each SGX block (P7D-006).

The recovered public `psb-firmware-0.30-4.fc11` source package contains exactly `msvdx_fw.bin` and `COPYING`; its spec installs only `msvdx_fw.bin` under `/lib/firmware`. The candidate 4.41.1 kernel source requests that name in `psb_msvdxinit.c:239–247,328–357`, under an MSVDX firmware-upload path. Therefore this **specific package** supplies an MSVDX/video payload, not an identified SGX535 microkernel. It does not prove that SGX needs no separate program or that another package cannot contain one (P7D-007). The proprietary payload bytes were inspected only through archive inventory and were not added to the repository.

The retained `Xpsb.so` contains an XHW shared BO, direct `XHW_INIT`/`XHW` requests, SGX-register initialization code and the [440-byte static upload](static-buffer.md). The retained `psb_dri.so` contains generated USC/USSE and PDS-related userspace paths. The stronger 5.0.1.0046 PSB kernel-source candidate contains command, XHW, scene, BO and fence handlers. Those facts constrain the historical division of work, but do not establish the complete SGX bring-up dependency order, an SGX microkernel identity, or that all needed payloads are present. No firmware was loaded or executed here.

Outstanding static targets are the exact built `libdrm.so.2` and DDX, the matching built PSB kernel module, any separate SGX bootstrap payload or generated initializer, and the full XHW request/reply data flow. Package names alone cannot settle those dependencies. The historical `psb-firmware` question is resolved only for the recovered 0.30-4 package: it is the MSVDX file described above.

The later [P7E draw/submit trace](../psb-dri-re/draw-to-submit.md) adds a **userspace ordering**: DRI context setup installs the renderer and frame tracker; entering mode 3 creates a scene; leaving mode 3 finalizes that scene and submits an index-0 0x90-byte request. It does not prove that XHW has completed initialization, that SGX is powered/clocked, that any microkernel is present, or that the kernel accepts the request. Those are still pre-first-submit dependencies for a hypothetical clean-room path. No new reason emerged to reopen the MSVDX package inventory or to label the Xpsb 440-byte source as firmware.
